# --- NLP & RAG Embeddings ---
# C1.2 (2026-09-28): torch 2.9.1+cpu -> 2.10.0+cpu — remediates CVE-2026-24747 (fixed in
# 2.10.0) with no new HIGH/CRITICAL in Docker Scout; still CPU-only (+cpu wheel, no
# nvidia-*/triton). CVE-2026-4538 (affects <=2.10.0, no upstream fix) remains a documented risk.
# torch: CPU-only build, pinned by exact local version identifier (+cpu).
# Docker optimization 2026-09-21 (Issue DOCKER-CPU-001): plain `torch==2.9.1`
# resolved from default PyPI on manylinux (this image's python:3.11-slim base)
# to the CUDA 12.8 build (torch 2.9.1+cu128), pulling in the full
# nvidia-*-cu12 stack + triton as direct deps of that wheel (~8.9GB alone;
# confirmed via `pip show torch` inside the built image: Requires includes
# nvidia-cublas-cu12, nvidia-cudnn-cu12, nvidia-nccl-cu12, triton, etc.) even
# though torch.cuda.is_available() is always False in this deployment target
# (no GPU) — dss/core/models.py already only *conditionally* uses CUDA when
# available (`if dss_config.torch.cuda.is_available(): ... else: ...`), so
# nothing in the application requires the GPU build. Pinning the LOCAL
# version identifier itself (`==2.9.1+cpu`), resolved from the official
# CPU wheel index below, is what actually prevents this from silently
# reverting to the GPU build on a future `pip install -r requirements.txt`
# (even with --upgrade, as long as this pin stays) — a plain `torch==2.9.1`
# would still match the GPU wheel's public version and pip would happily
# re-resolve it from default PyPI. See
# reports/production_readiness/DOCKER_CPU_ONLY_PYTORCH_OPTIMIZATION.md.
--extra-index-url https://download.pytorch.org/whl/cpu
